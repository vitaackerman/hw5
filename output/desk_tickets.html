Reflection

This is based on the Problem 9 run: the Expected and Actual sections in the ticket tabs, the Cash tab, resolved_tickets.json and run entries 105–307 of audit_trail.json. Every number below comes from those.

1. How the agents did on each ticket

Ticket 101, Bulldog tee

It worked pretty well overall, but it was more complicated than it needed to be. The agents got the important things right:

  • Inventory saw there were 0 size S shirts.
  • Accounting dealt with the $840 invoice 501 by making request PR-1 instead of trying to pay it.
  • Customer service drafted D-1 to Tauhid.
  • Nothing got shipped. ship_order never even got called, because there was no stock.

The annoying part is it took 3 runs:

  • Run 1 got it to waiting_on_approval.
  • After I approved PR-1, run 2 rechecked and kept it in_progress, because the shirts still weren’t there.
  • Then we had to stop and figure out what “resolved” even means when the reprint hasn’t actually arrived. Only run 3 resolved it, and inventory threw in a vendor status draft (D-4) along the way.

Across the 3 runs that’s 27 model requests, 24 tool calls and about 78k tokens for one t-shirt. The agents weren’t wrong, the ticket just can’t really finish in this app, which comes back in question 5.

Ticket 102, Rent due

This is the clearest example where having multiple agents was kind of unnecessary.

  • Facilities checked the rent, then also checked the cash with get_cash_and_obligations and made payment request PR-2 itself.
  • Meanwhile accounting got called and mostly checked the same cash situation again ($2,560, leaves $160).
  • In the second run the boss called get_cash_and_obligations itself and facilities called it again too. That’s 4 cash checks for one rent payment.

It still worked: the boss rechecked and saw payment #2 and next_due moved to 2026-10-02 before resolving, and I still had to approve the $2,400 myself. But one agent with the right tools probably could have done the whole thing. It was 2 runs, 17 model requests, 16 tool calls and about 46k tokens.

Ticket 103, Bulk hoodies

Having multiple agents made more sense here, because there were actually different questions to answer:

  • Inventory had to check whether we could supply 20 hoodies: 8 in size M, 12 short.
  • Accounting had to look at the discount and margin: $22 cost, $58 list, 62.1% max before losing money.
  • The boss had to choose the discount: 15%, so $49.30 each and $986 for 20.
  • Customer service had to write the final response.

It still got a little messy. Customer service tried to delegate back to the boss to ask about the discount, and that got blocked because the boss was already above it in the chain. So it wrote D-2 saying the discount was “under review”, and only after the boss sent it back did we get the real one, D-3. Now there’s an outdated draft sitting there that someone could send by accident. This was also the most expensive ticket: 29 model requests, 29 tool calls and about 91k tokens over 2 runs, and the first run alone took about a minute.

Overall

My takeaway is that multiple agents are useful when the jobs are actually different, but if the task is simple it just creates extra steps and duplicate work. I also thought the safety parts worked better than the coordination parts:

  • Every dollar that left checking was something I clicked approve on: $840 plus $2,400, so $3,400 down to $160 in the Cash tab.
  • Every message stayed a draft (D-1 to D-4).
  • The agents couldn’t invent stock, because there’s literally no tool for it.
  • They couldn’t move money on their own: request_payment never touched cash before I approved.

The coordination is where the weird stuff happened: repeated cash checks, a refused delegation, an extra draft, and an extra run while we figured out what resolved means.

3. What would have been simpler as one agent with tools

Ticket 102 is the main example. The whole ticket is basically:

  1. Read it (get_ticket).
  2. Check cash (get_cash_and_obligations).
  3. Request the rent (request_payment).
  4. Wait for me to approve.
  5. Recheck.
  6. update_ticket.

One agent with those tools could do that in a straight line. With the team it went boss → facilities and boss → accounting, and the cash got checked 4 times by 3 different agents without anyone finding anything new.

It also wouldn’t be less safe, because the safety is in the MCP server, not in having more agents: request_payment can’t move money, approve_payment is human-only, and update_ticket won’t resolve while a request is pending.

Parts of 101 could probably have been done by one general operations agent with the same tools too: check_stock, get_cash_and_obligations, request_payment and create_draft. A lot of the handoffs just meant re-reading the same stuff. In runs 2 and 3, inventory called get_ticket again, and in run 3 the boss called check_stock itself after inventory already had.

Where splitting it up actually helped was 103. Because customer service can’t make the pricing call, it didn’t quote a discount on its own; D-2 said “under review” instead of making up a number. So the split mattered most when there was a real decision that should belong to someone else.

4. Three new problems this team could already solve

These assume the request shows up as a row in the tickets table like our 3 did, since there’s no create-ticket tool.

  1. A customer orders a Yale Cap. CC-HAT-BLUE has 40 in stock and no invoice mentions it, so inventory could check_stock and actually call ship_order for real, which never happened in our run. Customer service would draft a confirmation and the boss would resolve. Also, since invoice 501 is paid now, an order for the white tee in a size that’s in stock (M has 5) would ship too. Before the payment, ship_order would have blocked every CC-TEE-WHITE size, because 501’s description names the SKU.
  2. October’s rent notice. Lease 1’s next_due is now 2026-10-02 for $2,400, but checking only has $160 (bottom of the Cash tab). Facilities and accounting would find this with get_ticket and get_cash_and_obligations. request_payment would refuse with “Not enough cash”, and the boss would keep the ticket open and flag it for me. The team can’t fix the cash problem, but it would catch it and not pay, which is the right behavior.
  3. Another bulk discount request, like a club wanting 50 Yale Caps or 10 Crest Mugs. It’s the same shape as 103. check_stock shows caps at 40 (10 short) and mugs at 0. get_pricing with discount_pct gives the room: caps cost $6 and list at $22, mugs cost $3.50 and list at $14. The boss picks the discount and customer service drafts the reply. For mugs, inventory would get Elm City Gifts’ 3 lead days from the vendors info.

5. Three problems this team couldn’t solve, and what it would need

  1. Adding stock to inventory. This is literally why 101 got stuck. When Bulldog Print Co’s reprint actually shows up, nothing can add it, because the only stock-changing tool is ship_order, which subtracts. So 101 got resolved on paperwork and the tee can still never ship. It would need a receive_stock tool that a human confirms (or that’s tied to a delivery record and the paid invoice), plus something to place restock orders. A procurement/receiving agent could own ordering and receiving, and that would also cover the 12 missing hoodies from 103.
  2. Adding money to cash. Cash only goes out in this app. Even if the club accepts the $986 quote from 103, it never shows up in checking, so we’re stuck at $160 with October rent coming. It would need a sales/order agent with order tools (create an order, record a sale) and a cash-in tool to record deposits. There should probably be an orders table, and a human confirmation before cash goes up, the same way approvals work for money going out. Then accounting could plan payments around real income.
  3. Processing a return or refund. Say Tauhid gets the tee and wants to return it. There’s no orders table to look up what he bought, no way to put the item back in stock, and no refund tool. It would need a returns agent with a return tool (look up the order, put the item back into inventory after checking it) and a refund tool. The refund is money going out, so it should go through human approval like request_payment and approve_payment do now. Customer service would still just write the draft to the customer.
